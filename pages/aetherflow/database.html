Connection & Transaction Strategy

Connection-Per-Request Pattern

Request Lifecycle

1
Request arrives at API
2
Create fresh database connection
3
Execute stored procedure
4
Close connection
5
Return response

Design Philosophy

  • • No shared state between requests
  • • Eliminates race conditions
  • • Simple error handling
  • • Clean transaction boundaries
  • • Predictable behavior

Benefits & Rationale

Why This Approach

  • • Eliminates connection pooling complexity
  • • Prevents transaction interference
  • • Clear error boundaries per request
  • • Simplified state management
  • • Suitable for current scale

Future Enhancement Path

  • • Connection pooling for high-traffic scenarios
  • • Long-running query monitoring

No Dirty Records

No partial saves or intermediate states. Complete interactions only. All-or-nothing approach ensures data consistency.

Stored Procedures Architecture

Database-First Approach

52 Stored Procedures

Complete abstraction layer for all database operations

• Equipment allocation logic
• Availability checks
• Driver task management
• Quality control workflows
• Customer/site selection
• Hire interaction processing

Design Philosophy

Every database operation goes through stored procedures - no direct table access

  • • Complete data access abstraction
  • • Complex business logic orchestration
  • • Consistent error handling patterns
  • • Performance optimization at database level
  • • Security through controlled access
